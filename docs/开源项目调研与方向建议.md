## 一、当前架构的核心瓶颈（先诊断，再开药）

### 1.1 通信层：文件轮询是最大性能瓶颈

**现状**：
- Python 端写 `lua_cmd.txt`，DLL 端每 50ms 轮询检查文件
- DLL 执行后写 `lua_result.txt`，Python 端轮询读取
- 单次命令往返：100-500ms（取决于轮询时机）
- 资源状态刷新：3 秒/次（因为通信慢，不敢刷太快）

**为什么这是瓶颈**：
- 所有功能都受限于通信延迟——点按钮后要等半秒才生效
- 资源监控不实时，看到的是 3 秒前的状态
- 未来做游戏内 overlay、实时属性查看器，都需要毫秒级通信

**成熟项目怎么做**：
- **REFramework**：DLL 注入后 Lua 直接在游戏主线程执行，外部工具通过命名管道通信
- **Cyber Engine Tweaks**：共享内存 + Win32 Event 通知，命令往返 < 5ms
- **UE4SS**：named pipe 用于外部 GUI 与游戏内通信

**建议方案**：
```
Python (命名管道服务器)  <-->  DLL (命名管道客户端)
       \\.\pipe\woldvein_trainer

- Python 端：CreateNamedPipe + 重叠 I/O，多线程处理
- DLL 端：CreateFile 连接管道，工作线程 ReadFile 阻塞等待
- 协议：4字节长度 + JSON body（与当前文件协议兼容，便于迁移）
- 文件轮询保留作 fallback（管道连接失败时自动降级）
```

**预期收益**：命令往返 100-500ms → 5-20ms，资源刷新 3s → 500ms

**实施难度**：中等。Windows 命名管道 API 成熟，DLL 端需新增一个工作线程。

---

### 1.2 偏移稳定性：硬编码偏移，游戏更新即失效

**现状**：
- `lua_pcall` 的地址通过导出表查找（`GetProcAddress`）
- 游戏全局变量名（`g_camp`、`g_Time`）硬编码在 Lua 脚本中
- 如果游戏更新改了导出表或变量名，修改器直接失效

**成熟项目怎么做**：
- **UnknownCheats x64 Internal Lua Engine Hook**（JX3 项目）：
  - 偏移每次小版本更新都变
  - 实现 **Dynamic RIP Resolver**：pattern scanner 解析 RIP-relative 指令，自动定位 `lua_loadstring` 和 `lua_pcall`
- **UE4SS**：
  - **SinglePassScanner**：多线程 AOB 模式匹配，`VirtualQuery` 遍历内存区域，通配符支持
  - 签名扫描在运行时动态定位关键函数，不需要硬编码地址
- **SigMaker Pro**（CE 插件）：
  - 自动计算唯一签名所需最小字节数（动态长度，不是固定 64 字节）
  - 用 Zydis 反汇编器分析指令，生成稳定签名
- **风灵月影**：
  - 启动时"等待一段时间"就是在做特征码扫描确定偏移
  - 这是商业修改器的标准做法

**建议方案**：
```
1. 在 DLL 端实现 AOB 扫描器：
   - 输入：IDA 风格特征码 "48 89 5C 24 ? 48 89 6C 24 ?"
   - 遍历：VirtualQuery 枚举可读写内存区域
   - 匹配：字节比较，? 通配任意字节
   - 优化：多线程扫描不同内存区域

2. 对关键函数做特征码备份：
   - lua_pcall、luaL_loadstring 的特征码
   - 导出表找不到时，自动用特征码扫描定位

3. 扫描结果缓存：
   - 首次扫描后缓存地址，后续直接使用
   - 游戏版本变化时自动重新扫描
```

**预期收益**：游戏小版本更新后修改器仍能工作，不需要重新硬编码偏移

**实施难度**：中高。AOB 扫描器本身不难（~100行C代码），难在找到稳定的特征码。

### 1.3 Lua 执行：当前方式的局限与优化空间

**现状**：
- DLL Hook `lua_pcall`，Python 端通过文件发送 Lua 代码
- DLL 在 Hook 回调中检测到命令文件，调用原始 `lua_pcall` 执行
- 返回值只能是数字或字符串，table 需要手动拼 JSON

**成熟项目怎么做**：
- **Love2D Cheat Toolkit**（Open Cheat Tables）：
  - Hook 一个被频繁调用的 Lua C 函数（`lua_gettop` 最理想），窃取其第一个参数得到 **live lua_State**
  - 然后用 `luaL_loadstring` + `lua_pcall` 执行任意 Lua
  - 注入的 Lua 可以直接访问游戏的全局变量、table、LuaJIT FFI
- **Where Winds Meet**（UnknownCheats）：
  - MinHook Hook `lua_pcall`，在 hook 中执行自定义代码
  - PatternScan 定位 `lua_load` 和 `lua_pcall`
  - 支持 Lua 脚本热重载
- **Civ5 Lua Modding**：
  - 获取 lua_State 指针后，只需 `luaL_loadbuffer` + `lua_pcall` 两个函数就能执行任意脚本
- **饥荒 LuaJIT 桥接**（掘金，深度技术文章）：
  - 与 woldvein 技术路线完全一致：inline hook LuaJIT 函数 → 获取 lua_State → 执行自定义 Lua
  - 包含完整的 5 字节跳转 hook 代码：`0xe9` + 相对地址计算
  - 详细讲了如何搜索目标函数并与 luajit 连接，处理寄存器保护
  - **这是中文社区最接近 woldvein 架构的实战文章**

**当前架构的优点**：
- Hook `lua_pcall` 的方式是对的，能拿到合法的 lua_State
- 在游戏主线程执行，线程安全

**可优化点**：
1. **返回值序列化**：当前只能回数字/字符串，应实现通用的 Lua table → JSON 序列化（递归遍历，处理循环引用）
2. **执行超时保护**：恶意/死循环 Lua 会卡死游戏主线程，应设置执行超时（用 `lua_sethook` 计数指令数）
3. **错误处理增强**：`lua_pcall` 失败时，用 `lua_tolstring` 获取完整错误信息和调用栈，传回 Python 显示

**实施难度**：低-中等。都是 Lua C API 的标准用法。

### 1.4 开发效率：猜字段名是最大的时间浪费

**现状**：
- 添加新功能需要知道游戏的全局变量名和字段结构
- 目前靠猜、靠试、靠零散的探针输出
- 比如 `cheat_tools.py` 里的 `set_prosperity` 写 `g_camp.prosperity`，但这个字段是否存在从未验证

**成熟项目怎么做**：
- **UE4SS Live View**：
  - 树状结构列出所有 UObject，可搜索/展开/编辑
  - 右键属性 → "Watch" 监视变化
  - 这是 modder 最常用的工具，开发效率提升巨大
- **Cyber Engine Tweaks RTTI Inspector**：
  - 浏览运行时类型信息，查看所有类/方法/属性
  - TweakDB Editor 可视化编辑游戏数据库
- **REFramework Game Object Browser**：
  - 遍历游戏对象树，查看/编辑字段

**建议方案：实现「Lua 探查器」**
```
功能：
1. 输入全局变量名（如 g_camp），递归遍历所有字段和方法
2. 树状展示，可展开/折叠，处理循环引用（用 visited 表）
3. 可编辑字段值（数字/字符串/布尔）
4. 可"监视"字段，定时刷新并高亮变化
5. 导出探查结果为 JSON，供开发参考

技术实现：
- Lua 端：用 pairs() 遍历 table，对每个值做 type() 判断
  - number/string/boolean → 直接返回值
  - table → 递归遍历（带深度限制，默认 3 层）
  - function → 返回函数地址和 upvalue 数量
  - userdata → 尝试用 getmetatable 查看元表
- Python 端：ttk.Treeview 展示树，双击编辑
```

**预期收益**：新功能开发速度提升 5-10 倍，不再靠猜字段名

**实施难度**：中等。Lua 端遍历 + 循环引用处理是核心，Python 端 Treeview 是标准控件。

### 1.5 UI 操作：Alt+Tab 切屏体验差

**现状**：
- 修改器是独立 tkinter 窗口
- 玩游戏时要切出来操作，再切回去
- 全屏游戏下切屏可能卡顿或崩溃

**成熟项目怎么做**：
- **REFramework**：Hook DX11/12 Present，ImGui 渲染游戏内 UI，Insert 键呼出
- **Cyber Engine Tweaks**：overlay 含 Console/Logs/TweakDB Editor，游戏内直接操作
- **hudhook (Rust)**：`hudhook!(ImguiDx11Hooks, MyRenderLoop)` 一行宏接入，支持 DX9/11/12/OpenGL

**DX Hook 标准流程**（所有项目都一样）：
```c
// 1. Hook IDXGISwapChain::Present（渲染回调）
// 2. Hook IDXGISwapChain::ResizeBuffers（窗口大小变化时重建）
// 3. Hook WndProc（捕获键盘鼠标，Insert 键切换显示）
// 4. ImGui 初始化：
//    ImGui_ImplWin32_Init(hwnd)
//    ImGui_ImplDX11_Init(device, context)
// 5. 在 Present hook 中：
//    ImGui_ImplDX11_NewFrame()
//    ImGui_ImplWin32_NewFrame()
//    ImGui::NewFrame()
//    // 你的 UI 代码
//    ImGui::Render()
//    ImGui_ImplDX11_RenderDrawData(ImGui::GetDrawData())
```

**建议方案（分阶段）**：
- **阶段 1（最小可用）**：只做资源条，半透明固定屏幕顶部，不可交互，仅显示金钱/木料/食物/水/人口/幸福度
- **阶段 2（可交互）**：热键呼出完整面板，可点击按钮执行常用操作
- **阶段 3（完整控制台）**：Lua 实时执行 + 日志 + 对象浏览器

**实施难度**：高。需要逆向游戏的 DX 设备指针，但 REFramework 和大量开源示例可参考。

## 二、功能层面的可借鉴方向

### 2.1 预设系统（Profiles）

**现状**：每次打开都要重新点按钮，没有保存/加载配置的能力。

**成熟项目**：
- YimMenu：所有设置序列化为 JSON，支持多 profile
- CheatGear：多个修改项保存为预设方案，一键应用
- 风灵月影：预选设置，启动后自动应用

**实现**：
- 保存当前所有修改项状态（创造模式开关、资源值、时间速度等）为 JSON
- 预设文件放 `profiles/` 目录
- 启动时自动加载上次使用的预设
- 内置几个常用预设："满资源开局"、"创造模式全开"、"纯建造辅助"

**难度**：低。纯 Python 层。

---

### 2.2 Lua 脚本生态（用户可扩展）

**现状**：所有 Lua 脚本硬编码在 Python 文件中，用户无法自定义。

**成熟项目**：
- REFramework：`autorun/` 目录自动加载，`re.on_frame(fn)` 事件回调，脚本热重载
- YimMenu：`scripts/` 目录自动加载，完整 Lua API 文档
- Cheat Engine Lua：条件逻辑（资源低于阈值自动补充）、自定义热键

**实现**：
- 新增 `scripts/` 目录，用户放入 `.lua` 自动加载
- 提供 Lua API 封装：
  ```lua
  wv.on_update(function() end)              -- 定时回调（可配置间隔）
  wv.get_resource("money")                  -- 获取资源
  wv.set_resource("money", 999999)          -- 设置资源
  wv.execute_lua("g_camp.m_nMoney = 1")     -- 执行原始 Lua
  wv.register_hotkey("F1", function() end)  -- 注册热键
  wv.log("message")                         -- 日志
  ```
- 脚本热重载：文件修改后自动重新加载
- 脚本错误隔离：单个脚本出错不影响其他脚本

**难度**：中等。DLL 端实现 Lua API 绑定，Python 端管理脚本。

---

### 2.3 操作历史与撤销

**现状**：修改后无法撤销，改错了只能手动改回去或读档。

**实现**：
- 记录每次修改操作（时间、操作类型、旧值、新值）
- 支持"撤销此操作"按钮，恢复旧值
- 操作历史可导出为日志

**难度**：低。

---

### 2.4 诊断与稳定性

**成熟项目的通用做法**：
- **风灵月影**："安全模式"防崩溃
- **REFramework**：脚本错误直接显示，不崩游戏
- **GoldHEN (PS4)**：Master Code 设计、内存安全、渐进式测试

**建议实现**：
1. **Hook 健康检查**：启动后自动检测 lua_pcall Hook 是否生效，失败则提示并自动回滚
2. **诊断包导出**：一键打包日志+配置+进程信息+DLL版本+游戏版本+最后执行的 Lua 命令
3. **崩溃记录**：游戏崩溃时记录最后执行的 Lua 命令（需要 DLL 端在执行前写入"最后命令"文件）
4. **安全模式**：启动时按住 Shift 跳过所有自动应用的修改
5. **Lua 执行超时**：用 `lua_sethook` 限制指令数，防止死循环卡死游戏

**难度**：低-中等。

## 三、架构层面的改进建议

### 3.1 中心协调器（减少模块间耦合）

**现状**：`trainer_ui_tk.py` 直接调用各个模块（`resource_editor`、`creative_mode`、`advanced_tools`），模块间相对独立但没有统一协调。

**成熟项目**：
- REFramework 有中心 `REFramework` 类管理所有子系统
- BepInEx 有清晰的分层：preload → core → plugin → services

**建议**：
- 引入 `GameContext` 单例，统一管理：
  - 注入状态（是否已注入、DLL 版本、游戏 PID）
  - 通信通道（管道/文件）
  - 游戏状态缓存（最近一次状态刷新结果）
  - 事件总线（模块间解耦通信）
- 各模块通过 `GameContext` 获取依赖，不直接互相调用

**难度**：中等。重构工作量大但收益明显。

---

### 3.2 事件总线（模块间解耦）

**现状**：模块间直接调用，比如资源修改后需要通知状态刷新模块，目前是直接调用函数。

**成熟项目**：
- REFramework/CET 都有事件回调系统（`re.on_frame`、`RegisterForEvent`）
- ghook-sdk 有类型安全的扩展注册表

**建议**：
- 实现简单的事件总线：
  ```python
  bus = EventBus()
  bus.on("resource_changed", lambda res, old, new: ...)
  bus.emit("resource_changed", "money", 100, 999999)
  ```
- 模块间通过事件通信，降低耦合
- 未来 Lua 脚本也可以订阅/发布事件

**难度**：低。~50 行代码。

## 五、最值得立即做的三件事

### 1. 命名管道通信（投入产出比最高）

**为什么**：
- 当前文件轮询是整个系统的性能瓶颈，所有功能都受限于 100-500ms 延迟
- 改完后资源刷新可以从 3 秒/次提到 500ms/次
- 操作响应从"点了等半秒"变成"点了立即生效"
- 这是未来做 overlay、实时监控、脚本生态的基础

**怎么做**：
- Python 端：`CreateNamedPipe` + 重叠 I/O，独立线程处理连接
- DLL 端：`CreateFile` 连接管道，工作线程 `ReadFile` 阻塞等待命令
- 协议：4 字节长度前缀 + JSON body（与当前文件协议兼容）
- 文件轮询保留作 fallback，管道连接失败时自动降级

**风险**：低。Windows 命名管道是成熟 API，REFramework/CET/UE4SS 都在用。

---

### 2. Lua 探查器（开发效率提升最大）

**为什么**：
- 当前添加新功能全靠猜字段名，`cheat_tools.py` 里至少 3 个函数写的字段可能根本不存在
- 有了探查器，可以直接在游戏里探索 `g_camp`、`g_Time`、`g_LBuildingCardManager` 的真实结构
- 新功能开发速度提升 5-10 倍
- 这是开发者工具，对用户透明，但能加速整个项目的迭代

**怎么做**：
- Lua 端：`pairs()` 递归遍历 table，处理循环引用（visited 表），限制深度
- Python 端：`ttk.Treeview` 展示树，双击编辑值，右键"监视"
- 结果可导出为 JSON

**风险**：低-中。主要工作量在循环引用处理和 UI 展示。

---

### 3. AOB 特征码扫描（稳定性提升最大）

**为什么**：
- 当前 `lua_pcall` 靠导出表查找，游戏更新改了导出就失效
- 风灵月影等商业修改器都用特征码扫描，这是行业标准
- 改完后游戏小版本更新不需要重新硬编码偏移
- 这是修改器"耐用性"的关键

**怎么做**：
- DLL 端实现 AOB 扫描器：`VirtualQuery` 遍历内存 + 字节匹配 + `?` 通配
- 对 `lua_pcall`、`luaL_loadstring` 记录特征码
- 导出表找不到时自动用特征码扫描定位
- 扫描结果缓存，避免每次都扫

**风险**：中。扫描器本身不难，难在找到稳定的特征码（需要用 CE 或 x64dbg 分析）。

### RDTSC 时间检测详解（新增）
**原理**：
`c
unsigned __int64 t1 = __rdtsc();
// ... 被调试的代码 ...
unsigned __int64 t2 = __rdtsc();
if ((t2 - t1) > THRESHOLD) exit(0);  // 单步执行慢，时间差大
`

**绕过方法**：
1. **Hook RDTSC**：Hook rdtsc指令，返回递增的合理值（ScyllaHide支持）
2. **硬件断点**：在第二次rdtsc后设硬件断点，修改eax寄存器
3. **Frida hook**：用Frida替换时间函数返回值
4. **Hypervisor层欺骗**：Ring -1 hypervisor拦截RDTSC VM-exit，返回一致时间戳（Denuvo用此技术）
5. **补丁比较指令**：NOP掉条件跳转，或强制阈值为最大值

**对woldvein的意义**：如果平野孤鸿有RDTSC检测，注入DLL后单步执行会触发。woldvein可以在DLL中Hook RDTSC返回合理值，或用ScyllaHide的思路综合绕过。

### Hook 检测与反检测（新增）
| 检测方法 | 原理 | 反检测方法 |
|---------|------|-----------|
| **IAT Hook检测** | 检查导入表函数地址是否在模块范围内 | 用Inline Hook替代IAT Hook，或恢复IAT后再调用 |
| **EAT Hook检测** | 检查导出表函数地址是否被修改 | 少用EAT Hook，或用代理DLL |
| **Inline Hook检测** | 校验函数序言字节是否为0xE9(jmp)/0xCC(int3) | UnhookNtdll恢复原始字节，或用硬件断点/VEH替代 |
| **系统调用Hook检测** | 检查ntdll.dll的syscall指令是否被hook | Direct Syscall（SysWhispers3）直接调用内核，绕过ntdll |
| **Trampoline检测** | 检查函数是否跳转到模块外内存 | 用模块内内存分配trampoline，或用VEH |

### 对 woldvein 的实际意义（新增）
1. **注入时绕过反调试**：如果平野孤鸿有反调试机制，woldvein的DLL注入可能被检测。可以参考ScyllaHide的思路，在DLL中综合绕过PEB标志、NtQueryInformationProcess、RDTSC等检测。
2. **woldvein自身加反调试**：防止修改器被逆向分析，可以加简单的IsDebuggerPresent检测和PEB检查。
3. **Hook稳定性**：当前woldvein用5字节跳转Inline Hook lua_pcall，如果游戏有Hook检测会被发现。可以考虑用VEH或硬件断点替代，或用UnhookNtdll思路。
4. **Direct Syscall**：如果需要调用敏感API，可以用SysWhispers3生成直接系统调用，绕过ntdll的Hook检测。

### 存档逆向方法论（新增，重点）
**步骤1：定位存档文件**
- Process Monitor监控文件IO，过滤游戏进程，找CreateFile/ReadFile/WriteFile
- 常见路径：%LOCALAPPDATA%、Documents\My Games、游戏目录\save

- 用ImHex/010 Editor打开存档，看是否有明文（JSON/XML/字符串）

- API Monitor监控游戏的文件API调用

**步骤5：编写解析器**
- 用Kaitai Struct写.ksy格式描述，编译成Python/C#解析器

## 新增章节：内核驱动注入（高优先级调研）

### 一、为什么需要内核驱动？

**用户态注入的局限**：
- OpenProcess 可能被反作弊的 ObRegisterCallbacks 拦截，strip 掉 PROCESS_VM_READ/WRITE 权限
- DLL 注入（CreateRemoteThread）会触发 PsSetLoadImageNotifyRoutine 回调
- 用户态调试器（DebugActiveProcess）容易被 IsDebuggerPresent 等检测

**内核驱动的优势**：
- Ring 0 权限，可以直接读写任意进程物理内存，不需要句柄
- 可以注册/修改内核回调，绕过反作弊的进程保护
- 可以操作 DR0-DR7 硬件断点寄存器，用户态无法修改
- 可以隐藏进程/模块/线程（DKOM）

**代价**：
- 需要驱动签名（微软控制），或利用有漏洞的已签名驱动（BYOVD）
- 开发复杂度高，蓝屏（BSOD）风险大
- 现代反作弊（EAC/BattlEye/Vanguard）会检测内核异常

---

### 二、驱动加载方式

#### 2.1 KDMapper（最流行的手动映射工具）

| 项目 | 说明 |
|------|------|
| **作者** | TheWover |
| **原理** | 利用有漏洞的已签名驱动 iqvw64e.sys（Intel网卡驱动）实现内核任意地址写，然后手动映射未签名驱动 |
| **流程** | 加载漏洞驱动 → 分配内核内存 → 复制驱动各section → 解析导入表 → 调用DriverEntry → 卸载漏洞驱动 |
| **优点** | 不需要测试模式，不需要重启，不需要自己的签名证书 |
| **缺点** | 漏洞驱动可能被微软拉黑（HVCI），映射的驱动不在PsLoadedModuleList中易被检测 |

**使用命令**：
`
kdmapper.exe "C:\path\to\your_driver.sys"
`

**检测向量（反作弊如何发现KDMapper驱动）**：
1. 驱动不在 PsLoadedModuleList 中（未注册模块）
2. 驱动内存是 RWX（可读可写可执行），正常驱动是 RX
3. 调用栈追踪：栈回溯到未注册模块的地址
4. PiDDBCacheTable / MmUnloadedDrivers 残留记录
5. g_KernelHashBucketList 哈希校验

**隐藏技巧**：
- 映射前清零 BaseDllName.Length，避免 MiRememberUnloadedDriver 记录
- 分配内存后改保护为 RX（去掉W）
- 伪造 .pdata 节，让栈回溯能正常展开

#### 2.2 DSE Bypass（驱动签名强制绕过）

| 方法 | 说明 |
|------|------|
| **Patch CiValidateImageHeader** | 在 SeCiCallbacks 中找到签名验证函数，patch 返回值，然后正常 NtLoadDriver |
| **gdrv.sys（技嘉）** | 另一个有漏洞的已签名驱动，用于DSE bypass |
| **efidsefix** | 通过EFI禁用驱动签名强制（需要重启） |
| **测试模式** | cdedit /set testsigning on，最简单但有水印且易被反作弊检测 |

#### 2.3 DBVM（Cheat Engine 内核虚拟机）

| 项目 | 说明 |
|------|------|
| **全称** | Dark Byte Virtual Machine |
| **类型** | Type-1 Hypervisor（Ring -1），基于 Intel VT-x / AMD-V |
| **原理** | 在操作系统之下运行一个超轻量虚拟机，Windows跑在Guest中，Cheat Engine通过自定义指令获得内核权限 |
| **特点** | 不虚拟设备，透传中断，性能影响极小 |
| **用途** | 内核级调试、硬件断点、绕过反调试、Ultimap代码追踪 |
| **限制** | 可能被EAC等内核反作弊检测（hypervisor存在性检测）、部分硬件/BIOS不兼容、可能BSOD |

**DBVM vs KDMapper**：
- DBVM是Ring -1，比内核更高，理论上更难检测
- KDMapper是Ring 0，利用漏洞驱动，实现更简单
- DBVM需要在启动时加载（USB或驱动方式），KDMapper运行时加载

### 三、内核回调与反作弊保护机制

#### 3.1 四大内核回调

| 回调API | 作用 | 反作弊用途 |
|---------|------|-----------|
| **ObRegisterCallbacks** | 进程/线程句柄操作回调 | OpenProcess时strip VM_READ/VM_WRITE/DUP_HANDLE权限 |
| **PsSetCreateProcessNotifyRoutine** | 进程创建/退出通知 | 检测可疑进程（调试器、注入工具） |
| **PsSetCreateThreadNotifyRoutine** | 线程创建/退出通知 | 检测远程线程注入（CreateRemoteThread） |
| **PsSetLoadImageNotifyRoutine** | 镜像加载通知 | 检测DLL注入（非游戏目录的DLL被加载） |

#### 3.2 ObRegisterCallbacks 详解

这是**反作弊最核心的进程保护机制**：

`
反作弊驱动注册回调 → 用户调用 OpenProcess(game_pid, VM_READ) 
→ 内核触发 PreOperation 回调 → 反作弊strip掉 VM_READ 权限 
→ 返回的句柄没有读权限 → ReadProcessMemory 失败 (ACCESS_DENIED)
`

**绕过方法（内核DKOM）**：
1. 在 PsProcessType 对象中找到 CallbackList（偏移 +0xC8）
2. 遍历 OB_CALLBACK_ENTRY 链表
3. 通过 Altitude 字符串识别反作弊的回调（如EAC的 328010）
4. Patch PreOperation（+0x28）和 PostOperation 指针为 dummy 函数
5. 之后 OpenProcess 就能获得完整权限

**实战案例**：XC3Killer（补丁Xigncode3的回调）、Valthrun（CS2内核读取）

#### 4.1 方法对比

| 方法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **MmCopyVirtualMemory** | 内核API，跨进程内存拷贝 | 官方API，稳定 | 需要进程对象，可能触发回调 |
| **物理内存读写** | 遍历页表，直接操作物理页 | 不需要句柄，完全隐蔽 | 实现复杂，需处理PAE/页表 |
| **KProcessReadWrite** | 附加到目标进程上下文 | 直接用用户态指针 | 上下文切换有开销 |

### 一、为什么需要游戏内 Overlay

**当前痛点**：woldvein 是外部 tkinter GUI，玩家修改参数需要 Alt+Tab 切出游戏，影响体验。

**Overlay 优势**：
- 在游戏画面上直接渲染半透明面板，不需要切窗口

- 全局热键呼出/隐藏（如 Insert 键），不干扰游戏操作

**代价**：
- 需要在注入的 DLL 中加 DX Hook + ImGui 渲染逻辑（C++ 开发）
- 不同图形 API（DX9/DX11/DX12/Vulkan/OpenGL）需要不同 Hook
- 全屏独占模式、HDR、多显卡等兼容性问题

### 二、DX11 Overlay 核心原理（平野孤鸿用 DX11）

#### 2.1 Hook 目标：IDXGISwapChain::Present

| 项目 | 说明 |
|------|------|
| **Hook 函数** | IDXGISwapChain::Present |
| **虚表索引** | **8**（固定，所有 DX11 游戏通用） |
| **同时 Hook** | IDXGISwapChain::ResizeBuffers（索引13，处理窗口大小变化） |
| **Hook 方法** | 虚表指针替换（VTable Hook） |

#### 2.2 虚表 Hook 流程

`
1. 创建临时 D3D11 设备和 SwapChain（用 CreateWindow + CreateDeviceAndSwapChain）
2. 从临时 SwapChain 读虚表地址：void** vtable = *(void**)swapChain
3. 保存原始函数：oPresent = (Present_t)vtable[8]
4. 替换虚表：VirtualProtect(&vtable[8], 8, PAGE_READWRITE, &old)
             vtable[8] = (uintptr_t)hkPresent
             VirtualProtect(&vtable[8], 8, old, &old)
5. 释放临时设备
`

#### 2.3 Present 回调中的 ImGui 渲染

`cpp
HRESULT __stdcall hkPresent(IDXGISwapChain* sc, UINT sync, UINT flags) {
    if (!g_imgui_init) {
        // 跳过前120帧，等D3D稳定
        if (++g_frame_count >= 120) {
            InitImGui(sc);  // 创建ImGui上下文+DX11后端
            g_imgui_init = true;
        }
        return oPresent(sc, sync, flags);
    }
    
    // 开始ImGui帧
    ImGui_ImplDX11_NewFrame();
    ImGui_ImplWin32_NewFrame();
    ImGui::NewFrame();
    
    // 绘制自定义面板
    if (g_overlay_visible) {
        ImGui::Begin("woldvein Trainer");
        ImGui::Text("金钱: %d", g_money);
        if (ImGui::Button("+100万")) { /* 执行Lua */ }
        ImGui::End();
    }
    
    // 渲染
    ImGui::Render();
    ImGui_ImplDX11_RenderDrawData(ImGui::GetDrawData());
    
    return oPresent(sc, sync, flags);
}
`

#### 2.4 输入处理

| 方法 | 说明 |
|------|------|
| **WndProc Hook** | 子类化游戏窗口，捕获键鼠消息传给 ImGui |

## 新增章节：操作日志与撤销机制

### 一、为什么需要撤销机制

**当前痛点**：woldvein 的修改操作是"单向"的——点了"+100万"就改了，想改回去只能手动输入原值，容易出错。如果改错了（比如把幸福度改成0），可能导致游戏异常。

**撤销机制的价值**：
- 误操作一键回滚，降低试错成本
- 操作历史可追溯，知道"刚才改了什么"
- 批量操作（如"一键全部资源拉满"）可以整体撤销
- 调试时可以对比修改前后的状态

---

### 二、两种核心设计模式

#### 2.1 Command Pattern（命令模式）— 推荐

每个用户操作封装为一个命令对象，包含 execute() 和 undo() 方法，用两个栈管理：

`
用户操作 → 命令对象.execute() → 压入 undo 栈 → 清空 redo 栈
撤销(Ctrl+Z) → undo 栈弹出 → 命令对象.undo() → 压入 redo 栈
重做(Ctrl+Y) → redo 栈弹出 → 命令对象.execute() → 压入 undo 栈
新操作 → 清空 redo 栈（时间线分叉）
`

**命令对象结构**：
`python
class IUndoAction:
    def execute(self): pass   # 执行操作
    def undo(self): pass      # 撤销操作
    def description(self): pass  # 显示在历史列表中
`

**优点**：内存占用小（只存差异，不存完整状态）、撤销速度快
**缺点**：每个操作类型都要写一个命令类

#### 2.2 Memento Pattern（备忘录模式）— 快照

操作前保存完整状态快照，撤销时恢复快照：

`
操作前 → 保存当前状态（深拷贝）→ 执行操作 → 快照压入栈
撤销 → 弹出快照 → 恢复状态
`

**优点**：实现简单，不需要为每个操作写undo逻辑
**缺点**：内存占用大（完整状态拷贝），适合小数据量

**优化**：增量差异（Incremental Diff）——只保存改动的部分，不存完整快照。

---

### 三、woldvein 的四类撤销场景

#### 3.1 内存修改撤销（最简单，优先做）

`python
class MemoryEditAction(IUndoAction):
    def __init__(self, address, old_value, new_value, data_type="int"):
        self.address = address
        self.old_value = old_value
        self.new_value = new_value
        self.data_type = data_type
    
    def execute(self):
        write_memory(self.address, self.new_value, self.data_type)
    
    def undo(self):
        write_memory(self.address, self.old_value, self.data_type)
    
    def description(self):
        return f"内存修改 [{hex(self.address)}]: {self.old_value} → {self.new_value}"
`

**关键点**：修改前先读旧值，操作完成后连同新值一起记录。

#### 3.2 存档修改撤销（已有基础，加恢复按钮）

woldvein 已有存档备份功能，撤销就是恢复备份：

`python
class SaveEditAction(IUndoAction):
    def __init__(self, save_path, backup_path):
        self.save_path = save_path
        self.backup_path = backup_path  # 修改前的备份
    
    def execute(self):
        # 已在外部执行，这里只记录
        pass
    
    def undo(self):
        shutil.copy(self.backup_path, self.save_path)  # 恢复备份
    
    def description(self):
        return f"存档修改: {os.path.basename(self.save_path)}"
`

#### 3.3 Lua 执行撤销（最复杂，需要设计）

woldvein 大部分操作是通过 Lua 脚本执行的（如 g_camp.money = 999999），Lua 执行的副作用不可预测。

**方案 A：执行前后内存对比**
- Lua 执行前快照关键内存区域
- 执行后对比差异
- 撤销时把差异改回去
- 缺点：需要知道哪些内存区域是"关键"的

**方案 B：每个 Lua 操作显式记录修改字段**
- 封装 Lua 操作接口，执行时记录"改了哪个全局变量的哪个字段"
- 撤销时执行反向 Lua 脚本（如 g_camp.money = 原值）
- 缺点：需要改造所有 Lua 调用点

**方案 C：只支持"可预测"的 Lua 操作撤销**
- 资源修改、数值调整等简单操作支持撤销
- 复杂 Lua 脚本（如创造模式开关）不支持撤销，提示"此操作不可撤销"
- **推荐**：先做这个，覆盖80%场景

#### 3.4 开关/标志撤销（最简单）

`python
class FlagToggleAction(IUndoAction):
    def __init__(self, flag_name, old_state, new_state):
        self.flag_name = flag_name
        self.old_state = old_state
        self.new_state = new_state
    # execute/undo 就是设置对应状态
`

### 四、事务（Transaction）：批量操作打包

**问题**："一键全部资源+100万"实际执行了10个内存写入，如果撤销时只撤销最后一个，资源还是多了900万。

**解决方案**：事务——把多个操作打包为一个撤销单元：

`python
class Transaction:
    def __init__(self, description):
        self.actions = []
        self.description = description
    
    def add(self, action):
        self.actions.append(action)
    
    def execute(self):
        for a in self.actions:
            a.execute()
    
    def undo(self):
        for a in reversed(self.actions):  # 逆序撤销
            a.undo()

# 使用
tx = Transaction("一键全部资源+100万")
for res in resources:
    tx.add(MemoryEditAction(res.address, old, new))
tx.execute()
undo_stack.push(tx)  # 整个事务作为一条历史记录
`

### 五、操作日志系统

#### 5.1 日志条目结构

`python
@dataclass
class LogEntry:
    timestamp: datetime      # 精确到毫秒
    operation_type: str      # "memory_write" / "save_edit" / "lua_exec" / "flag_toggle"

| **搜索** | 按关键词/时间搜索 |
| **导出** | 导出为 JSON/文本，用于调试排错 |
| **持久化** | 保存到本地文件，重启修改器后保留历史 |
| **颜色分级** | 信息灰、修改黄、错误红 |

- 撤销栈 = 日志中 undoable=true 且 status=success 的条目

### 六、关键设计细节

#### 6.1 栈上限与内存控制

`python
MAX_UNDO_STACK = 50  # 最多保留50条，超出丢弃最旧的
`

- 内存修改操作很小（几十字节），50条可以忽略
- 存档备份较大，需要单独控制（如最多5个备份，自动删除最旧的）

#### 6.2 校验与自动回滚

| 阶段 | 校验 |
|------|------|
| **修改前** | 校验数值范围、数据类型、地址有效性，非法直接拦截 |
| **修改后** | 读回确认写入成功，失败自动回滚并提示 |
| **撤销前** | 校验地址/文件是否仍然有效（游戏是否还在运行、存档是否被覆盖） |

#### 6.3 编辑锁

撤销/重做过程中禁止新操作，防止状态混乱：
`python
class UndoManager:
    def __init__(self):
        self._editing = False  # 编辑锁
    
    def undo(self):
        if self._editing: return
        self._editing = True
        try:
            # 执行撤销
        finally:
            self._editing = False
`

#### 6.4 非线性历史（进阶）

不只是"一步步撤销"，而是可以点击历史列表中的任意节点直接跳转：
- 从当前状态到目标节点，自动计算需要撤销/重做哪些操作
- 在旧节点上做新修改时，自动丢弃后续重做栈（时间线分叉）

### 一、自动更新系统

#### 1.1 Python 自动更新方案对比

| 方案 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| **PyUpdater** | 专门为 PyInstaller 设计的自动更新框架 | 成熟、与PyInstaller深度集成、支持增量更新、TUF安全签名 | 维护放缓（作者转Go）、配置稍复杂 |

| **Esky** | 老牌Python自动更新框架 | 简单、pp.auto_update()一行调用 | **已停更**、不推荐新项目 |
| **dgupdater** | 低代码CLI更新工具 | 跨平台、增量更新 | 工具型，不是库 |
| **自己实现** | GitHub Release API + 下载 + 替换 | 完全可控、无依赖、适合小项目 | 需要处理文件锁、权限、回滚 |

#### 1.2 推荐方案：自己实现（基于 GitHub Release）

woldvein 已经托管在 GitHub，用 GitHub Release API 最直接：

`
流程：
1. 启动时（或手动点击"检查更新"）请求 GitHub API:
   GET https://api.github.com/repos/180lisilence/woldvein0.3-0.4/releases/latest
2. 解析 tag_name（如 v0.4.6），与本地 APP_VERSION 对比
3. 如果有新版本，显示更新提示 + 更新日志（release.body）
4. 用户确认后，下载 release 中的安装包（.exe 或 .zip）
5. 下载完成后，启动外部更新器（bat或小exe），关闭主程序，替换文件，重启
`

**关键技术点**：
- **文件锁问题**：EXE 正在运行时无法替换自身 → 需要外部更新器进程（updater.bat 或独立 updater.exe）
- **MoveFileEx API**：Windows 提供 MOVEFILE_DELAY_UNTIL_REBOOT，可在重启时替换被锁定的文件
- **回滚机制**：更新前备份旧版本，更新失败自动恢复
- **GitHub API 限流**：未认证请求 60次/小时，woldvein 用户量小，够用；可加 token 提升到 5000次/小时
- **代理支持**：国内访问 GitHub 可能需要代理，应支持读取系统代理或手动配置

## 新增章节：性能优化体系

### 一、woldvein 当前性能瓶颈分析

| 瓶颈 | 现状 | 影响 | 优先级 |
|------|------|------|--------|
| **文件轮询通信** | Python ↔ DLL 通过 lua_cmd.txt/lua_result.txt 轮询 | 命令往返延迟百毫秒级，连续操作卡顿 | **最高** |
| **内存读写** | 每次修改单独 ReadProcessMemory/WriteProcessMemory | 单次微秒级，影响小 | 低 |
| **UI 刷新** | tkinter 定时器轮询游戏状态 | 100ms 间隔，可接受 | 低 |
| **启动速度** | 全量初始化所有模块 | 1-2秒，可接受 | 低 |

**结论**：当前最大瓶颈是**文件轮询通信**，应优先替换为命名管道（Named Pipe）。

### 二、通信层优化（最高优先级）

**命名管道替代文件轮询**：
- DLL 端：CreateNamedPipe + ConnectNamedPipe，阻塞等待命令
- Python 端：win32file.CreateFile 打开管道，双向通信
- 协议：JSON 格式，含请求 ID（防止响应错位）
- 延迟从百毫秒级降至毫秒级

### 三、内存扫描优化（未来做特征码扫描时参考）

**Squalr 的经验（比 Cheat Engine 快 2.6 倍）**：
- SIMD 加速（SSE/AVX/AVX-512 一次比较 16/32/64 字节）
- 多线程并行（内存区域分片）
- 批量读取（64KB 一次 ReadProcessMemory，本地搜索）
- 智能区域过滤（跳过系统库、不可读页、Guard 页）

**关键优化清单**：限定模块范围（减少80%扫描量）、批量块读取（减少99%系统调用）、SIMD匹配（4-8倍速度）、多线程分片（线性加速）、异步扫描（不阻塞UI）。

### 四、内存读写优化

- 批量读取连续地址（1次系统调用 vs 10次）
- 进程句柄缓存（全局单例，不频繁 OpenProcess/CloseHandle）
- 模块基址/偏移表缓存（只查一次，常驻内存）
- 无效地址黑名单（读取失败的地址直接跳过）

### 五、Il2Cpp 优化（平野孤鸿是 Il2Cpp）

- 类/方法/字段偏移缓存（减少90%查表开销）
- 直接偏移读取替代反射调用（速度10-100倍）
- 批量字段读取（一个对象多字段一次读整块）
- 减少 il2cpp_runtime_invoke 高频调用（避免GC压力）
- 对象遍历降频（不每帧遍历，按需刷新）

### 六、ImGui/Overlay 渲染优化（未来做 Overlay 时）

帧率节流（30-60帧）、懒渲染（UI没变不重绘）、虚拟滚动列表（万级数据不卡）、对象池（消除每帧new/delete）、隐藏时暂停渲染。

### 七、IO 与配置优化

存档整块读取、配置常驻内存+延时写入（500ms防抖）、日志批量写入+环形缓冲区、异步备份/清理。

### 八、对 woldvein 的实施建议

**立即做（1-2天）**：命名管道通信、进程句柄缓存、配置常驻内存+延时写入。
**未来做**：特征码扫描优化、Overlay渲染优化、Il2Cpp直接读取。
**不需要做**：内核驱动级内存读写、超大规模扫描、复杂动态质量切换。

## 新增章节：安全加固体系

### 一、为什么需要安全加固

woldvein 当前缺少输入校验和操作保护，用户可能因为误操作导致：
- 输入非法数值（如负数、超大值）导致游戏崩溃
- 断电/程序异常导致存档损坏
- 误点"资源归零"等高危操作无法挽回
- 附加到错误进程导致其他程序异常

### 二、自身完整性校验

| 措施 | 说明 | 优先级 |
|------|------|--------|
| **主程序哈希校验** | 启动时计算自身EXE哈希，与内置值对比，检测篡改 | 低 |
| **DLL 完整性校验** | 注入前校验 DLL 文件哈希/签名 | 中 |
| **配置文件校验** | 加载配置时校验格式合法性，损坏则恢复默认 | 高 |
| **运行时自检** | 周期性检查内存中关键代码段是否被篡改 | 低 |

### 三、输入校验（最高优先级，低成本高收益）

| 校验 | 说明 |
|------|------|
| **地址合法性** | 写入前用 VirtualQueryEx 检查地址是否可读可写，拒绝内核地址/NULL |
| **数值范围** | 资源数值限制在合理范围（如 0 ~ 21亿），拒绝负数/超大值 |
| **数据类型** | 按字段类型校验（int/float/bool），类型不匹配拒绝写入 |
| **Il2Cpp 指针校验** | 检查对象 vtable 有效性，防止野指针 |
| **对象存活检测** | 操作前检查游戏对象是否已销毁 |
| **UI 输入净化** | 输入框拒绝非法字符、超长文本 |

### 四、存档安全

| 措施 | 说明 |
|------|------|
| **修改前自动备份** | 任何存档写入前自动复制备份（woldvein已有基础） |
| **原子写入** | 先写临时文件，校验成功后再替换原文件（防止断电损坏） |
| **存档校验和** | 写入后计算 CRC32/MD5，读取时验证完整性 |
| **写入前校验** | 检查存档文件头、版本号、大小是否合法 |
| **备份隔离** | 备份文件存独立目录，避免误删 |

### 五、操作安全

| 措施 | 说明 |
|------|------|
| **高危操作二次确认** | "资源归零""批量修改"等操作弹窗确认 |
| **热键防抖** | 全局热键加 200ms 防抖，防止重复触发 |
| **操作限额** | 单次批量修改限制最大数量（如最多100个地址） |
| **紧急停止按钮** | 一键终止全部内存写入、Hook、异步任务 |
| **只读模式** | 开关：仅查看内存，禁止任何写入（调试用） |
| **受限模式** | 禁用高危批量修改功能 |

### 六、进程与注入安全

- **进程白名单**：仅允许附加到 BalladsOfHongye.exe，拒绝其他进程
- **进程位数校验**：32/64位不匹配时拒绝注入
- **DLL 路径校验**：只加载程序目录内的 DLL，防止外部恶意替换
- **Hook 地址校验**：只允许 Hook 游戏模块内的地址
- **Hook 冲突检测**：检测目标地址是否已被其他 Hook，避免互相覆盖
- **Hook 卸载校验**：卸载时确认函数已恢复原始字节

### 七、文件与更新安全

- **路径净化**：阻止路径穿越攻击（..\）
- **写入沙箱**：文件写入仅限指定目录（程序目录、备份目录）
- **更新包哈希/签名校验**：下载后验证完整性，防止篡改
- **更新沙箱解压**：在隔离临时目录解压，校验完成再替换
- **原子文件替换**：更新时先写临时文件再替换，防止中断损坏
- **更新失败自动回滚**：更新异常时恢复旧版本

### 八、隐私与日志

- **日志脱敏**：不导出敏感内存原始指针、密钥
- **遥测默认关闭**：用户手动选择是否启用
- **错误报告过滤**：崩溃报告自动过滤敏感信息
- **日志文件只读权限**：防止外部篡改日志

### 九、对 woldvein 的实施建议

**立即做（1天）**：
1. 输入数值范围校验（资源/幸福度等输入框加 min/max）
2. 存档原子写入（先写临时文件再替换）
3. 高危操作二次确认（资源归零、批量修改）
4. 进程白名单（只允许附加到 BalladsOfHongye.exe）

**中期做（2-3天）**：
5. 地址合法性校验（VirtualQueryEx 检查）
6. 热键防抖
7. 紧急停止按钮
8. 配置文件损坏恢复默认

**不需要做**：
- 自身反调试/反 dump（修改器不需要保护自己不被逆向）
- 代码混淆/加壳（开源项目，没必要）
- 复杂的数字签名（个人项目，用哈希校验足够）

#### 3.2 故障排查（最有价值）

| 问题 | 排查步骤 |
|------|---------|
| **注入失败** | 1.是否管理员运行 2.杀毒是否拦截 3.游戏是否已启动 4.进程名是否匹配 |
| **修改无效** | 1.是否注入成功 2.游戏版本是否支持 3.是否在正确的页面/场景 4.查看日志 |
| **游戏崩溃** | 1.是否输入了非法数值 2.是否同时开了其他修改器 3.导出诊断包 |
| **热键失效** | 1.是否与其他软件冲突 2.是否在设置中改了热键 3.是否焦点在游戏窗口 |
| **存档损坏** | 1.从备份恢复 2.是否修改了存档后未正常保存 |
| **Overlay不显示** | 1.是否无边框窗口模式 2.是否关闭了Steam Overlay 3.图形API是否匹配 |
